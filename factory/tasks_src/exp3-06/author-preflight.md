## Native browser path

1. In the Bitbucket repository use **Pipelines**, which opens `/<workspace-slug>/<repo-slug>/pipelines`. History sorts by descending build number and offers Branch, Pipeline type, Status and Trigger filters. Build detail opens at `/<workspace-slug>/<repo-slug>/pipelines/results/<buildNumber>`; the route takes the numeric build number, not the internal run ID. Keep the session's `sid` on direct entry.
2. History and Run summary show only seven hash characters. Click the hash in **Run summary** to open the corresponding commit and verify the full hash in its heading. The commit route accepts an internal commit ID or full hash, and the native link uses the commit ID with `?branch=<name>`. Avoid relying on the seven-character display if two choices share the prefix.
3. On the failed build use **Rerun failed steps** and confirm the same label in the modal showing the build number. It stays on the existing build and selects the first retried step and its new attempt through `step` and `attempt` query parameters. Use the Attempt dropdown to inspect the previous failed attempt and the new result. The retry ordinal is persisted but the log UI labels the step attempt, such as **Attempt 2 · Successful**. **Rerun entire pipeline** creates a new numbered build with `trigger: "rerun"` and `rerunOfRunId`; **Run pipeline** starts a new manual build.
4. Open the ClickUp task, available directly at `/t/<taskId>`. In Activity use **Write a comment…** and **Send**. Enter also submits and Shift+Enter inserts a line break. The reducer appends a task comment with `parentType: "task"`, the existing task as `parentId`, `authorId`, text and creation time. The state store posts `set_current` to the same sid. Use `/go` after the save to verify server persistence, since the browser also caches state locally.

## Plausible near misses and grading

A concrete fixture pattern uses failed build **#482** for the approved historical commit on `release/nov-18`, with **#487** on the same branch but on the newer tip and **#484** on a release-candidate branch at the same approved commit. Both decoys can be truly retryable with the same displayed failed step and different retry log lines. If adding a fourth run with the same exact repo, branch, commit and failed status, add a decisive run discriminator such as the named validation pipeline or push trigger in the source evidence. Adjacent build numbers alone do not resolve a tie.

- Grade the target run at its stable seeded ID and repo-local build number. Check identity fields and original logs, exactly one appended retry group, `number: 1`, `stepIds` containing exactly the seeded failed step, the expected outcome, and one new step attempt with `number: 2` and `retryId` equal to the group's generated ID. Assert the observed log line and status from actual appended attempt data. A successful retry leaves other attempts and steps unchanged.
- Reject extra pipeline mutations by comparing the complete run ID set and unchanged non-target run records to the baseline. Wrong-run retries can leave that run successful with convincing logs. A whole rerun appends a run and leaves the source failed. The intended delta is one retry group on the target.
- Independently check one new top-level comment on the seeded ClickUp parent from the seeded viewer. Require the batch/target tuple, build number, failed step name, attempt number, observed status and distinguishing retry log evidence according to the task's wording. Accept natural-language formatting, and compare full commit identity case-insensitively if applicable. Prefer asserting exact evidence tokens over inferring private navigation or comparing generated IDs, timestamp strings, and formatting against a golden answer.
- Excel workbook opening may write last-opened metadata and an operation. Mattermost reading may update read markers. If grading source preservation, compare source content fields rather than whole state objects.
